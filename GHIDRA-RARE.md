# TI TMS34010 processor module for Ghidra

A SLEIGH processor module for the Texas Instruments TMS34010 Graphics System Processor (GSP),
the CPU of many late-1980s/1990s arcade boards (Midway T/Y/Wolf units, Atari Games), TIGA PC
graphics cards and boards like the Amiga A2410. It is a community module that Ghidra-Rare
imported, tested against MAME and real code, and largely rewrote:

- [ZPaul2Fresh8/Ghidra_TMS34010](https://github.com/ZPaul2Fresh8/Ghidra_TMS34010) by ZPaul2Fresh8.
- Apache-2.0.
- See [CREDITS.md](CREDITS.md) for the upstream commit, the references used and every change.
- It targets Ghidra 12.1.4, and also builds on 12.1.3 and 12.2. Prebuilt zips are on the fork's
  [Releases page](https://github.com/aleph-void/Ghidra_TMS34010/releases).

The TMS34020 is not covered (it adds instructions and changes some encodings; MAME's
`tms34020` disassembler shows the differences).

## Language

| Language ID | Description |
|---|---|
| `tms34010:LE:32:default` | TMS34010, little endian, 32-bit bit addresses |

There is no ELF or COFF opinion: TMS34010 code comes as ROM images (import them as raw binary)
or as TI COFF files, which Ghidra does not load (see "Known gaps").

### Memory model: Ghidra address = bit address / 8

The TMS34010 addresses memory in bits. Registers, the PC, the stack pointer and every address
in an instruction are bit addresses. Ghidra cannot address bits, so the single `ram` space is
byte addressed and **a Ghidra address is the bit address divided by 8**. MAME's PC (a bit
address) is 8 times the Ghidra address.

- Import a ROM at Ghidra address = its bit address / 8. For example, a program ROM mapped at
  FF800000h goes at 1FF00000h.
- I/O registers (bit C0000000h) are at 18000000h; the pspec creates that block and names the
  32 registers. The trap vectors (bit FFFFFFE0h - 32N) are at 1FFFFFFCh - 4N.
- `ghidra_scripts/TMS34010Vectors.java` marks the vectors of an imported image and creates a
  function at each target. `ImportSymbols_Py3.py` (PyGhidra) and `ImportSymbols.py` (Jython)
  import a `TYPE|NAME|BITADDRESS|COMMENT` symbol list.
- Branch and call targets are shown as Ghidra addresses, so labels work.
- Absolute data operands (`MOVE @addr`) are shown as the bit address the instruction holds, as
  TI's assembler and MAME print them.
- Pointers in registers stay bit addresses, so the decompiler shows memory accesses as
  `*(T *)(ptr >> 3)` (see "Known gaps").

## Files

- `data/languages/tms34010.slaspec`: registers, the status register as separate fields (N, C,
  Z, V, PBX, IE, FS0/FE0, FS1/FE1), I/O register addresses.
- `tms34010.sinc`: instruction set and helpers (field and byte access at any bit address).
- `tms34010_mm.sinc`: MMTM/MMFM register-list tables, generated by `tools/gen_mm.py`.
- `tms34010_gfx.sinc`: PIXT, DRAV, CPW, CVXYL, LINE, FILL and PIXBLT.
- `tms34010.pspec`: I/O register block (volatile) and names, vector labels.
- `tms34010.cspec`: TMS34010 C compiler convention. A8 holds the return value; every other
  register is preserved; SP is the system stack.

## What is decoded

Every opcode MAME's TMS34010 core implements (`test/mame_core_table.txt`), with MAME's operand
order. Syntax follows TI's assembler where MAME differs:

- `JRUC`/`JAUC` (MAME prints `JR`/`JA`).
- `*Rd.XY` (MAME prints `*Rd,XY`).
- MMTM/MMFM list every register (MAME writes runs as `A0-A3`).

As in TI's assembler and MAME:

- `CLR Rd` is `XOR Rd,Rd`; `INC`/`DEC` are `ADDK`/`SUBK 1`.
- ANDI, CMPI and SUBI show the value, not the stored 1s complement.
- BTST K, SRA K and SRL K show the bit number or shift count.

Reserved opcodes (MAME's `unimpl`/`illop`) do not decode.

## Semantics

Everything has p-code:

- Arithmetic and logic: all flags as the User's Guide defines them, including ADDC/SUBB/NEGB
  carry and borrow.
- Shifts and rotates.
- MPYS/MPYU (multiplier of FS1 bits, 64-bit result in Rd:Rd+1).
- DIVS/DIVU (64/32 into an even register pair, or 32/32 for an odd register).
- MODS/MODU, LMO.
- Field moves in all 18 addressing modes (FS/FE from ST, any bit address), byte moves, MOVI,
  MOVK, MOVX/MOVY, cross-file MOVE.
- SETF, EXGF, SEXT, ZEXT.
- MMTM/MMFM.
- CALL/CALLA/CALLR, RETS N, RETI.
- TRAP N (vector fetch, PC and ST pushed, ST reset to 00000010h).
- JUMP, EXGPC, GETPC, GETST/PUTST, PUSHST/POPST, EINT/DINT, SETC/CLRC.
- JRcc/JAcc, DSJ/DSJEQ/DSJNE/DSJS, REV.
- XY instructions: ADDXY/SUBXY/CMPXY flags, CPW outcodes, CVXYL with CONVDP, PSIZE and OFFSET.
- PIXT (all 6 forms), DRAV, LINE 0/1, FILL L/XY and the six PIXBLTs. These cover:
  - All 22 pixel-processing operations.
  - Transparency and plane masking.
  - Window modes W=0-3. A violation sets V and INTPEND.WVP.
  - PBH/PBV directions with corner adjustment.
  - Binary expansion with COLOR0/COLOR1, and FILL's COLOR1 pattern.
  - The completion registers from the User's Guide.

EMU is a no-op, as it is when no XDS emulator drives the RUN/EMU pin.

## Test results

Run `test/run-tests.sh` for everything except real code, and `test/fetch-real-samples.sh`, then
`test/real-binaries.sh` for real code (see "Testing").

### Decoding vs MAME

The oracle is MAME 0.285 `unidasm -arch tms34010`. Each corpus record is a 9-word slot: the
opcode, four random extension words and four NOPs, so MAME's linear sweep stays in step.

| Corpus | Records | Same instruction | Both invalid | Explained | Unexplained |
|---|---|---|---|---|---|
| table: every opcode 0000h-FFFFh | 65,536 | 52,992 | 12,064 | 480 | 0 |
| fuzz: random opcodes | 50,000 | 40,409 | 9,211 | 380 | 0 |

"Same instruction" means the same text after normalisation. The normalisations are:

- Branch targets: Ghidra's address × 8.
- The three syntax conventions above.
- Numbers compared by value; a 16-bit immediate MAME prints unsigned matches Ghidra's signed
  value modulo 2^16.

The explained classes are all MAME display issues (see "Confirmed reference-tool bugs"):

1. MAME's disassembler decodes opcodes that its own core treats as reserved. These are NOP,
   CLRC, DINT, EINT, SETC, EMU, POPST, PUSHST, RETI, CALLA, CALLR, MOVB @,@ and MOVE @,@ with
   the B-file bit set, and LINE, FILL and PIXBLT with "don't care" bits that the core checks.
   Ghidra follows the core and rejects them (384 table opcodes).
2. MOVB @SAddress,Rd (07E0h) is printed as MOVE (32 opcodes).
3. SRA/SRL K with a count field of 0 is printed as `20h`; MAME's core shifts by 0, as the
   field's 2s complement says, and Ghidra prints 0 (64 opcodes).

The original module agreed with MAME on 86.42 % of the table corpus (8,486 opcodes differed).
As imported it did not load in Ghidra 12 at all: its pspec failed validation.

**Every-entry test** (`test/entry_check.py`): all 330 SLEIGH constructors (instruction and
operand subtables) are used by at least one decoded instruction of the table corpus.

### Assembler corpus (NetBSD gspa)

`test/gen_asm.py` writes every instruction form that NetBSD's TMS34010 assembler `gspa`
accepts, with random operands and labels: 1,644 instructions in 12 rounds. `gspa` assembles
them, and `test/asm_check.py` compares Ghidra's decode at each address with the source line and
with MAME.

| Check | Result |
|---|---|
| vs the assembler source | 1,644 / 1,644. The comparison normalises aliases, number bases, label targets and gspa's own DSJ-to-DSJS shortening (12 cases) |
| vs MAME | 1,631 identical; 13 in the explained classes 2 and 3 |

### Emulator

`test/emu_tests.py` and `test/EmuCheck.java` run 98 sequences in Ghidra's p-code emulator.
The expected values were worked out by hand. Twenty of them are the User's Guide's own
examples (names ending in `_ug`). They cover:

- ADD/ADDC/SUB/SUBB/NEG/NEGB/ABS flags, including overflow and carry-in edge cases.
- Complemented immediates.
- Logic, BTST, every shift and rotate form.
- MPYS/MPYU with FS1, DIVS/DIVU (64-bit, odd register, overflow, divide by 0), MODS/MODU, LMO.
- SEXT/ZEXT.
- Field stores and loads at bit offset 5, with sign extension, post-increment, pre-decrement,
  offsets and absolute addresses; MOVB at a bit offset.
- MMTM/MMFM.
- CALLA/CALLR/CALL with RETS and RETS N, TRAP/RETI with a vector, PUSHST/POPST/PUTST/GETST,
  EXGF (guide examples).
- DSJ/DSJS loops, DSJEQ/DSJNE, signed and unsigned JRcc, long JR, JAcc, GETPC/JUMP, EXGPC.
- ADDXY/SUBXY/CMPXY flags, CPW, CVXYL.
- PIXT with XOR and the plane mask, and the PIXT window modes W=2/3 (guide examples).
- FILL L, and FILL XY with W=3 clipping and with the plane mask (guide examples).
- LINE window modes W=1/2/3.
- PIXBLT L,L overlapping copies with PBH=0 and PBH=1.

Results: 98/98. With `--break N` one expectation is made wrong, and the check then reports
exactly that test as failed.

### Graphics vectors (MAME-recorded)

[birdybro/TMS34010_sv](https://github.com/birdybro/TMS34010_sv) (MIT) publishes 137 test
programs, with the final machine state MAME recorded for each. They cover:

- Every PPOP × PSIZE combination.
- Every PIXT form, DRAV, LINE, both FILLs and all six PIXBLTs.
- Window modes, the plane mask, transparency, pitches, PBH/PBV directions and array edge cases.

`test/GfxCheck.java` runs each program in Ghidra's emulator and compares A0-A14, B0-B14, SP,
ST, the six graphics I/O registers and the 512 watched framebuffer words with MAME's results:

| Result | Cases |
|---|---|
| Identical to MAME | 119 |
| Identical except B10-B14 | 18 |
| Different | 0 |

After FILL and PIXBLT, B10-B14 hold intermediate values that the User's Guide leaves
undefined. The MAME build the vectors were recorded with leaves its own working image there;
this module leaves them unchanged.

### Real code

There is little freely licensed TMS34010 code. Commercial arcade and TIGA ROMs were not used.
The sample is NetBSD's program for the University of Lowell A2410 Amiga graphics board
(`grf_ultms.c`, generated from `grf_ultms.g`, BSD-2-Clause, Ignatios Souvatzis). It is fetched
from NetBSD at a pinned commit with SHA-256 checks and turned into a raw image at bit address
FFA00000h. NetBSD's gspa rebuilds the same words from the source, so the binary matches its
source exactly.

Results:

- 259 instructions found from the reset entry, every source instruction in the code block.
- 0 bad instructions, 0 error bookmarks.
- The function decompiles.
- Disassembly is 259/259 identical to MAME and to the assembler source at every address.

The program exercises:

- Field moves with both field sizes.
- PIXBLT B,XY and XY,XY, and FILL L/XY.
- MMTM/MMFM, CALL through a register, MPYU, CMPXY with JRC/JRV.
- Writes to the I/O registers.

## Upstream limitations and issues

- **README:** "Current status is incomplete, some semantics are still needed to be finished as
  well as other fixes." **Fixed.** Every instruction now has p-code, tested as above, and
  README.md marks this.
- **TODOs in the original spec:** JRcc long and DSJS targets "not calculating correctly",
  "pattern might be wrong as ANDNI is the same as ANDI", the MOVE @a,@b "equal constraint is
  impossible" error, SETF "if fieldsize = 0, then make it 32", and JUMP "will throw errors
  since register won't natively have a valid address". **All fixed** (rewrite).
- **Symbol scripts:** they divided by 8 and then masked to 1 MB. **Fixed**, see CREDITS.md.
- The repository has one issue, #1 (license request, closed after the author added
  Apache-2.0). It has no pull requests.

## Known gaps

These cannot be fixed in the module:

- **Interrupts.** LINE, FILL and PIXBLT run to completion in one step, which gives the same
  final state as the uninterrupted CPU. Ghidra models no interrupts, so the interruptible
  (PBX) resume path and interrupt delivery are not modelled. Window violations set
  INTPEND.WVP but raise nothing.
- **Hardware state.** I/O register side effects (video timing, host interface, DRAM refresh,
  shift-register transfers selected by DPYCTL.SRT) are not modelled. Graphics instructions
  read CONTROL, PSIZE, PMASK, CONVSP and CONVDP from the I/O block.
- **Bit-addressed pointers in the decompiler.** Ghidra cannot scale a pointer by 1/8, so
  memory accesses decompile as `*(T *)(p >> 3)`. Ghidra cannot recover the stack frame from SP
  or type pointers. For the same reason the TI C convention's arguments cannot become
  parameters: they are on the A14 program stack, a bit-addressed pointer.
- **Field sizes in the decompiler.** Field moves depend on FS/FE in ST. Within a function that
  executes SETF the decompiler folds them to constant sizes. At function entry they are
  unknown, so field moves before the first SETF decompile as generic bit-field code. The
  emulator is exact either way. *Set Register Values* on FS0/FE0/FS1/FE1 gives the decompiler
  the values; TI's C compiler keeps FS1 = 32.
- **Alignment assumption.** Stack and register-list transfers (PUSHST/POPST, CALL*/RETS/RETI/
  TRAP, MMTM/MMFM) treat the pointer as a multiple of 8 bits. TI requires MMTM/MMFM pointers
  to be word aligned, and every TMS340 toolchain keeps SP word aligned. Field and byte moves
  have no such assumption.
- **B10-B14 after FILL/PIXBLT** are left unchanged; the User's Guide calls them intermediate
  values.
- **Undefined cases follow MAME or are documented:** MMTM/MMFM with the pointer in the list
  (TI: "unpredictable"), PSIZE values other than 1/2/4/8/16, and REV (returns 8, the guide's
  example).
- **Not provided:**
  - A TI COFF loader. TI's toolchain writes COFF with bit addresses, which Ghidra's COFF loader
    does not handle, and there are no freely licensed TMS340 COFF files to test one against.
  - The TMS34020.

### Unverified

- Real commercial code (arcade, TIGA): none is freely licensed, and none was used.
- TI C compiler output: the compiler is not freely available. The cspec follows its manual.
- PIXBLT/FILL window modes W=1 and W=2, and PBV with PIXBLT L,L. These are implemented from
  the User's Guide and the TMS34010_sv notes. MAME's core logs W=2 as "not supported" and
  ignores PBV for L,L, and the vectors do not cover them. FILL XY with W=3 is checked against
  the guide's example.

## Confirmed reference-tool bugs

- **MAME 0.285 disassembler** (`34010dsm.cpp`):
  - It prints MOVB @SAddress,Rd (07E0h-07FFh) as `MOVE @addr,Rd`: the `case 0x01e0` branch
    for `op & 0x200` prints MOVE. Its core (`movb_ar_a/b`) executes MOVB, as the User's Guide
    says.
  - It prints SRA/SRL K with field 0 as `20h` (`print_constant_2s_comp` computes
    32 - field without masking). Its core shifts by `(-field) & 0x1f` = 0.
  - It decodes opcodes its core table marks `unimpl`. For example 0310h is "NOP" with the
    B-file bit set, and 0F10h is "PIXBLT L,L" with bit 4 set.
- **MAME core:** ADDC/SUBB/NEGB compute C (and NEGB's V) without the carry-in, unlike the User's
  Guide. For example, ADDC with Rs = FFFFFFFFh, Rd = 0 and C = 1 gives C = 0 in MAME and 1 on
  the CPU. Ghidra follows the guide (`test/emu_tests.py` `addc_cin_carry`,
  `subb_bin_borrow`). In PIXBLT/FILL, MAME's PPOP 13 is `~S & D` (the guide and MAME's own
  PIXT use `~S | D`). Its PPOP 19 is S - D (the guide: D - S, saturating). It ignores the plane
  mask.
- **NetBSD gspa:** `SUBI IW,Rd` with a destination other than A0 is assembled as 0CE0h|Rd, a
  reserved opcode, instead of 0BE0h|Rd. The fix-up in `gsp_inst.c` (`if (opc == 0x0CE0)`)
  runs after the register number has been ORed in. `test/run-tests.sh` shows it.
